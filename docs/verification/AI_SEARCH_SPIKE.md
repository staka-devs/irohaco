# 実機でのAI検索の技術スパイク

- 状態: 実施計画（まだ実行していない）
- 前提: DBの整合性の仕様（`database/DATABASE_DESIGN.md`）は承認済み。写真と動画の最初のインデックス作成はユーザーの操作で始める。APIは既定で無効。
- 目的: 動画のシーン検索、複数のEmbedding、セマンティックメモでの検索が、基準端末で実用になるかを検証する。

## 開発環境

Android Studio、Kotlin、Jetpack Compose、Media3 FrameExtractor、LiteRT-LM、Room、Android Macrobenchmark、プロファイラーを使い、GPUとCPUの性能と温度の挙動を比べる。最初に、基準端末のRAMの構成、OSとAndroidのAPIレベル、空きストレージ、GPUドライバー、モデルの形式と量子化を実測して記録する。

## 技術スパイクの順番

1. Spike A（画像のEmbedding）: EmbeddingGemma 2で、テキストから画像を検索する。日本語と英語で、100〜300枚の画像からなる再現できる小さな評価セットを使う。モデルを3回起動し、コールドとウォームのレイテンシー、RAM、電力を測る。
2. Spike B（動画の検索）: 長さ30秒〜60分の動画を10〜30本用意する。動画をチャンクに分け、シーンの変化と時間の間隔でフレームを抽出し、フレームのEmbeddingを作り、時刻付きの検索結果からMedia3のプレイヤーでシークする。短い場面を見落とさないかを評価する。
3. Spike C（複数のEmbedding空間）: 同じメディアを異なるModelProfileと空間で索引にし、検索のときに切り替える。切り替えにはモデルのロードに時間がかかることがあるので、索引を選ぶ時間と最初の推論の時間を分けて測る。
4. Spike D（メモとGPSなしでの検索）: ユーザーのメモ、OCR、日時、位置の根拠を組み合わせたハイブリッド検索を試す。人物や場所の幻覚と、根拠のない地名の断定を0件にすることを目標に測る。
5. Spike E（リソースの制限）: 長時間の連続したフレームの処理、発熱、OSによる中断、RAMの逼迫、再起動からの復旧、権限の取り消しを検証する。
6. Spike F（MediaStoreのデータの永続性）: 移動、名前の変更、権限の変更、SDの抜き差し、ファイルの複製、原本への書き戻しを繰り返し、タグと注釈の紐付けがおかしくならないかを検証する。
7. Spike G（リモートAPIの安全な分離）: 5つの形式の接続設定を登録し、用途ごとの許可がOFFなら、テスト環境でネットワークへのアクセスが起きないことを検証する。

## 測定項目

| 測定 | データと計測の方法 |
|---|---|
| 検索の精度 | Precision@10、Recall@20、MRR、GPSのない写真のRecall |
| 時刻の精度 | 正解のシーンに対する絶対誤差（秒）。±5秒以内を仮の目標として確かめる |
| 応答 | cold model load、warm query embedding、SQL search、end-to-endを別々に計測する |
| スループット | 1分あたりの画像の枚数、実時間1分あたりに処理できる動画の分数、1分あたりのフレーム抽出の回数 |
| リソース | peak RSS/PSS、温度、thermal status、battery%、disk usage、CPU/GPUのbackend |
| 実用性 | 途中での停止と再開、SDの抜去、権限の変更、部分的なアクセス、ストレージの満杯 |
| モデルの切り替え | 古い索引が準備中の新しい索引と共存すること、切り替え前と後のヒット数 |

数値は実測前の仮の目標である。同じ評価セットで、モデルとフレームの密度を変えたときの差を記録し、目標値はベースラインを取ってからADRにする。1本の動画のフレーム数に固定の上限は設けず、時間のチャンクごとの密度と容量の上限を調整する。

## データセットと合格の条件

- 個人の写真は外部APIに送らず、同意を得た、またはライセンスを確認したテスト素材を使う。
- 正解のセットを作るときは、見た目に「写っている」もの、EXIFから「確定」したもの、周辺の写真から「推定」したものを注釈で区別する。
- 画像のEmbedding検索、メモの検索、動画の該当位置への移動が、オフラインで端から端まで成功することを最低の合格条件とする。
- 権限のないアセットが検索結果、RAGの回答、外部への送信に入ったら不合格とする。
- モデルの切り替えや索引の再開でユーザーデータが1件でも失われたら不合格とする。
- 生成モデルの既定はE2Bで、E4Bは任意とする。基準端末の制約でE4Bが向かないときは、その根拠を測定して記録する。

## スパイクのあとの判定（Go/No-Go）

1. 検索と動画のシークが端から端まで動くことと、短いシーンのRecallを示す。
2. 発熱、ストレージ、バッテリーの問題が許容できるかを、データから判断する。
3. 画像のインデックスの密度、動画のサンプリングの密度、ANNへ移る条件をADRで確定する。
4. GoならKotlinとRoomの実装を本開発に進める。No-Goなら、抽出の密度、推論のバックエンド、量子化したモデルを選び直す。
