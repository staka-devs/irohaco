# 次々工程 — 実機AI検索技術スパイク

- 状態: 実施計画（未実行）
- 前提: DB整合性仕様（`database/DATABASE_DESIGN.md`）を承認済み。写真・動画インデックス初回実行はユーザー操作。API既定無効。
- 目的: **動画シーン検索・複数Embedding・セマンティックメモ検索が検証対象端末で実用になるか**検証する。

## 開発環境

Android Studio / Kotlin / Jetpack Compose / Media3 Frame Extraction / LiteRT-LM / Room / Android Macrobenchmark / profiler。GPU・CPUの性能・温度挙動を比較。まず検証対象端末のRAM構成、OS/Android API、空きストレージ、GPUドライバ、モデル形式/量子化を実測記録する。

## 技術スパイクの順番

1. **Spike-A: 画像Embedding**。EmbeddingGemma 2でテキスト→画像検索。日本語・英語で100〜300画像の再現可能な小規模評価セット。モデルを3回起動しcold/warm latency・RAM・電力を測定。
2. **Spike-B: 動画検索**。長さ30秒〜60分の動画10〜30件を用意。動画をチャンク分割→シーン変化/時間間隔でフレーム抽出→フレームEmbedding→時刻付き検索結果からMedia3 playerをseek。短い場面が見落とされないか評価。
3. **Spike-C: 複数Embedding空間**。同じメディアを異なるModelProfile/Spaceに索引化し、クエリ検索時に切替。切替にはモデルロード時間が必要な場合があるので**索引選択時間と初回推論時間を別々に測る**。
4. **Spike-D: コメント/GPSなし検索**。ユーザーメモ、OCR、日時、位置根拠を組み合わせるハイブリッド検索。人物・場所の幻覚、根拠なしの確定地名を0件目標で測定。
5. **Spike-E: リソース制限**。長時間の連続フレーム処理・発熱・OSによる中断・RAM圧迫・再起動の復旧性・権限取り消しを検証。

## 測定項目

| 測定 | データと計測方法 |
|---|---|
| 検索精度 | Precision@10、Recall@20、MRR、GPSなし写真のRecall |
| 時刻精度 | 参照シーンに対する絶対誤差（秒）、許容±5秒を仮目標として確認 |
| 応答 | cold model load / warm query embedding / SQL search / end-to-endを別計測 |
| スループット | 画像/分・動画分/実分、frame extract回数/分 |
| リソース | peak RSS/PSS、温度、thermal status、battery%、disk usage、CPU/GPU backend |
| 実用性 | 途中停止・再開、SD抜去、権限変更、部分アクセス、ストレージ満杯 |
| モデル切替 | 旧索引が準備中の新索引と共存すること、前/後のヒット数 |

数値は**実測前の仮目標**。同じ評価集合に対してモデル・フレーム密度の差分を記録し、目標値はベースラインの後でADR化する。サンプル動画1本に対する96フレーム固定上限は採用せず、時間チャンク単位の密度と容量上限を調整する。

## データセットと合格条件

- 個人写真を外部APIに送信せず、同意/ライセンス済みのテスト素材を使用。
- 視覚的に「写っている」、EXIFから「確定」、周辺写真から「推定」を注釈で区別して正解集合を作成。
- Embedding画像検索・メモ検索・動画ジャンプの**オフラインE2E成功**を最低合格条件とする。
- 権限外アセットが検索結果/RAG回答/外部送信へ流入したら不合格。
- モデル切替や索引再開に伴うユーザーデータ損失は1件でも不合格。
- 対応端末のハード制約でE4Bが不適ならE2B優先／E4B任意とし、その根拠を測定する。

## Spike後のゲート（Go/No-Go）

1. 検索と動画seekのE2E成立、および短いシーンのRecallを提示する。
2. 発熱・ストレージ・バッテリー問題が許容可能かデータから決定する。
3. 画像インデックス密度・動画サンプリング密度・ANN移行条件をADRとして確定する。
4. GoならKotlin/Room実装を本開発へ。No-Goなら抽出密度・推論バックエンド・量子化モデルを再選定。
